# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

The Electron app lives in `studynook/`. The repo root holds the README, `CHANGELOG.md` (the readable history; the early git history is rough), `THIRD-PARTY-NOTICES.md`, the LICENSE (MIT, copyright held by Amorgabab; keep that notice), `.github/` (CI plus issue and PR templates), and `docs/`, the GitHub Pages website (`docs/index.html` plus `docs/assets/` screenshots; engineering notes live in `studynook/docs/`). Run all npm commands from `studynook/`. `tests/pages.test.js` checks that the README, the site and the license stay consistent; if the UI changes a lot, retake the screenshots in `docs/assets/`.

## Commands (run from `studynook/`)

- `npm ci --ignore-scripts` — install dependencies without Electron's ~100 MB binary download (this is what CI does; the unit tests are plain Node). When you need to run or build the app, also run `node node_modules/electron/install.js`. Current majors: Electron 45, electron-builder 26, plus `rcedit` for the installer icon.
- `npm start` — launch the desktop app (`electron .`). Dev mode keeps data in `studynook/data/`.
- `npm test` — unit tests: `node tests/run.js`. There is no built-in filter; `run.js` requires every `tests/*.test.js` and exits explicitly when done. To run one file, write a one-off runner that defines `global.test`, `global.suite` and `global.expect` (as `run.js` does) and requires just that file.
- `npm run lint` — ESLint (`eslint.config.js`): unused/undefined names, duplicate keys, `var`, `==`. Keep it clean; CI (`.github/workflows/ci.yml`, Windows) runs `lint` + `test` on every push to `main` and every PR. A new folder of Node code (like `build/`) must be added to the Node group in `eslint.config.js`.
- `npm run smoke` — `node tests/smoke.js`. Boots store, session, guardian and the sync server in plain Node (no Electron) and talks to `127.0.0.1:47470` like the extension does. It does not detect a busy port: if another StudyNook (for example the installed app) holds 47470, its checks hit that app and fail confusingly. Close other copies first.
- `npm run dist` — build the Windows NSIS installer into `dist-installer/`. `Make-Installer.bat` wraps `npm install` + `npm run dist` for end users. electron-builder's own exe editing is off (`signAndEditExecutable: false`), so `build/afterPack.js` stamps the StudyNook icon and product name into `StudyNook.exe` with rcedit; without it the taskbar shows Electron's atom icon. Check a build with `(Get-Item dist-installer\win-unpacked\StudyNook.exe).VersionInfo`.
- `NOOK_SMOKE=1` makes the real Electron app quit after 6 s and write `data/smoke.log` (renderer console messages are logged there too).
- `node tools/build-icons.js <lucide icon-nodes.json>` regenerates the bundled icon set (see below).

## Architecture (big picture)

Three runtimes cooperate, and most features span more than one of them:

1. **Electron main process** (`app/main/`). `main.js` is the entry point: boot, session recovery, backups, windows, tray and reward/notification logic. It builds one `ctx` object and hands it to `ipc.js` (every `ipcMain` handler), `watch.js` (extension/browser/watchdog watchers) and `snapshot.js` (per-window state). Around them: `store.js` (single JSON file `data.json`, atomic writes, `sanitizeData` on load/import), `session.js` (focus timer engine, persists `session.json` every few seconds, written atomically through `atomic.js`), `guardian.js` (scans processes every `scanSec` and warns/kills distractions; decisions are in pure `planner.js`, process listing in `processes.js`), `sync-server.js` (localhost HTTP bridge on 127.0.0.1:47470 for the Chrome extension, token-protected), `watchdog.js` (detached helper that relaunches the app if it dies mid-session), `extfinder.js` (read-only check of whether the extension is installed/enabled in Chrome-family profiles), `lifecycle.js` (`data/lifecycle.log`), `note-files.js` (PDF attachments, see Notes below) and `bounds.js` (keeps the mini timer on screen).
2. **Renderer** (`app/ui/`). Plain HTML/CSS/JS, no bundler. `index.html` is the main window; `mini.html` is the floating timer; `reminder.html` is the app-warning card. `app/ui/js/views-*.js` hold the pages (Notes is in `views-manage.js`); `app/ui/help/help-<lang>.js` hold the Help articles. The renderer talks to main only through `window.nook`, exposed by `app/main/preload.js` (contextIsolation on, nodeIntegration off).
3. **Chrome extension** (`extension/`, Manifest V3). `background.js` polls the desktop app's bridge and builds declarativeNetRequest redirect rules from `rules.js`. When the desktop app is not running it falls back to its own "standalone" lists and timer. If the app disappears while a focus session was active it keeps blocking ("ghost focus", `ghostFocusActive`): until the end time the app last reported for a running focus, or up to 12 hours for a paused focus (any mode since 1.5.15: the app sends `blockActive` for every focus round). The popup and blocked page use `ui.css`, `icons.js` and their own small `i18n.js`; what the blocked page says in place of a countdown (counting down / paused / StudyNook closed / always on) comes from the pure `blocked/label.js`.

`app/shared/` holds pure modules loaded by main **and** the UI windows (UMD style): `progress.js`, `iron.js`, `taskdays.js`, `links.js`, `catalog.js`, `extwatch.js`, `uiprefs.js` (theme/language resolution), `i18n.js` + `lang/{en,ar,fr,es}.js`, and the generated `icons.js`. `extension/rules.js` is shared the same way: `main.js` requires it and the extension loads it via `importScripts`. Tests live in `tests/` and cover these pure modules plus the main-process logic directly.

### Cross-cutting rules that are easy to break

- **Adding an IPC channel** means three edits: a handler in `registerIpc()` in `app/main/ipc.js`, the name in the `INVOKE` set in `preload.js` (and in `ON` for main→renderer events), and the call in the renderer. A channel missing from the whitelist fails silently in the UI; `tests/ipc.test.js` fails if the whitelist and the handlers disagree. The one synchronous channel (`notes:saveNow`, used only while the window is closing) lives in the `SYNC` set, is called with `nook.sendSync`, and is handled with `ipcMain.on`; the same test checks it both ways.
- **Each window gets only the state it draws.** `snapshot.js` has `full()` for the main window and tiny `mini()`/`reminder()` states for the floating timer and warning card; `pushSnapshot()`/`snapshotFor()` in `main.js` pick the right one. If a small window starts reading a new field, add it to its snapshot (and the test). The 1 s `tick` goes only to the main and mini windows.
- **Unsent form text survives a redraw.** The page is rebuilt on every snapshot; give any new input that holds unsaved text a `data-draft="view:field"` key (steppers take a `draft` argument) and `renderView()` restores it. A form that is *submitted* must clear its own fields, or the restore puts the sent text back.
- **Process lists:** code that only *decides* uses `processes.listProcessesShared()` (≤1.5 s old, shared); code about to *kill* uses `listProcesses()` for a fresh list. `guardian.scan()` skips listing when no enabled entry can match. **Allowlist mode only closes programs with a visible window** (Windows): `listProcesses(undefined, {windows: true})` marks each row `hasWindow` from PowerShell's `MainWindowHandle`, and `planner.chooseTargets` with `requireWindow` skips rows where it is not exactly `true` (so an unknown answer closes nothing). Blocklist mode never needs it. `NEVER_KILL` is only a short list of names, not a real system-process check; do not rely on it alone.
- **Settings writes are validated in two places.** `settings:set` clamps or enum-checks every field (raw-value sections are listed in `RAW_SECTIONS`); `sites:set` checks enums and booleans and normalizes/dedupes lists; `sanitizeData` does the same at load and import. A new setting needs handling in both paths and a default in `defaultData()`.
- **All user-facing text goes through i18n.** Use `t('key')` in windows and `T('key')` in `main.js`; add the key to `lang/en.js` **and** `ar/fr/es`. `tests/ui-redesign.test.js` fails on missing keys, mismatched `{placeholders}` or unknown literal keys. Arabic is RTL, so CSS must use logical properties (`margin-inline-start`, `inset-inline-end`), never left/right. Help articles in all four languages must keep the same block structure (a test checks it).
- **Theme is resolved in one place.** `NookPrefs.resolveTheme(setting, systemDark, hour)` decides light/dark for every window; colours come only from the CSS tokens in `styles.css` (`:root` and `:root[data-theme="dark"]`). Don't reintroduce time-of-day backgrounds.
- **Icons are generated.** `app/shared/icons.js` and `extension/icons.js` are written by `tools/build-icons.js` and must stay identical; add a Lucide name to that script's list and re-run it. No emoji in UI source (a test checks).
- **Iron Session is the authority for locks.** `app/shared/iron.js` decides what is frozen (timer strictness, site blocking, app-list edits, the multi-day self-lock). Any write that could soften a rule during an Iron focus must go through the `Iron.*` helpers, which `main.js`, `store.js`, `session.js`, `guardian.js` and the UI share (`sync-server.js` does not use them; `store.enforceIron()` re-applies the rules on every write, including bridge writes).
- **Breaks cannot be paused (Iron or not), and pausing a focus never stops blocking.** `SessionEngine.pause()` refuses whenever the phase is not `focus`; `resume()` is never refused and `skip()` stays refused in Iron. The Focus page disables the button (`breakNow` in `views-home.js`) and the tray calls `pause()` too, so the rule lives in the engine. `isFocusPhase()` (a focus round exists, running or paused) is what `guardian.isArmed()` and `publicState().blockActive` (sent to the extension) use, so a paused focus keeps blocking; the breathe/allow-5-minutes escape hatches are separate and unchanged outside Iron. **`blockActive` means "a focus round exists", not "Iron".** Anything that only Iron may do (closing a browser whose extension went quiet in `watch.js` `enforceBlocker`, the "browser will close" note) must ask `session.ironActive()`; 1.5.15 read `blockActive` there and closed browsers in normal sessions. `tests/watch.test.js` drives the real watcher and engine to guard this.
- **Lists are frozen during any focus round, and in Iron also while the self-lock runs.** App lists go through `Iron.filterFrozenList`; website lists go through `Iron.freezeSites(before, after, focusRound)` (blocked sites can be added, never removed; the allowed list cannot change; with `focusRound` true, site blocking cannot be switched off and the list mode cannot be flipped). `settings:set` also keeps the app guard's `enabled` and `mode` while a focus round exists. Frozen = `session.isFocusPhase()` or the self-lock (`listsFrozenNow` in `ipc.js`, `_listsFrozen` in `sync-server.js`, `App.listsFrozen()` in the UI). Every writer applies it (`sites:set`, `POST /sites`); a new way of editing the lists must too. Breaks and idle leave the lists editable. The lock notices have two wordings: Iron's own (an Iron focus or the self-lock) and neutral `*.frozen*.focus` keys for a normal focus round; `App.frozenSuffix()` picks one. `tests/site-freeze.test.js` checks all of these.
- **Session recovery.** On boot `recoverInterruptedSession()` restores a persisted session (running or paused) instead of discarding it. `SessionEngine.restore()` rebuilds the countdown and **backdates `phaseStartAt` by the seconds already focused**; stamping it "now" made a second kill restore a full-length timer and lose the focused minutes. Changes to the session state shape must keep `restore()`, `persistState()` and `SessionEngine.recoverable()` in step. Ending a session deletes `session.json`, which is the watchdog's "don't restart" signal.
- **Sleep is not focus time.** The timer is wall-clock based (`endsAt - Date.now()`), so `SessionEngine._tick` measures the gap since its last tick (every `TICK_MS`); a gap over `SLEEP_GAP_MS` means the PC slept, and `_skipGap` moves `endsAt` and `phaseStartAt` forward by it (running sessions only; paused ones have nothing to shift) and logs `sleep-skipped`. Do not replace this with `powerMonitor` events alone: the tick gap also covers hibernate and a frozen process, and it is testable in plain Node (`tests/session.test.js`). A real check: freeze the dev app with `NtSuspendProcess` for 40 s and see that `remainingSec` only loses the running time.
- **The watchdog must exist before an End task lands.** `startWatchdogEarly()` in `main.js` starts it as soon as `session.json` says a session is active (a 2 s timer used to, which left the first seconds after launch unprotected); `watch.ensureWatchdog(true)` starts it when a session begins. Its crash-loop budget is 10 relaunches per 10 minutes, kept in `watchdog-history.json`; a launch by a person (no `--restarted-by-watchdog` flag) calls `Watchdog.resetHistory()`, so giving up once never leaves later kills with no relaunch. It is a speed bump, not a lock: killing every `StudyNook.exe` at once defeats it, and with no session nothing relaunches the app.
- **Window close:** with no session and nothing set to run "always", the X quits the app (`win:close` in `ipc.js`); otherwise it hides to the tray. Keep that consistent with Settings → General → "Keep running in the tray".
- **Window close is gated.** `main.js` blocks closing the main window while any session exists (running or paused), and during an Iron focus it routes through a typed gate first.
- **Mini timer.** `mini.html`'s pill is the `-webkit-app-region: drag` handle; the egg (`#stage`) is `no-drag` and is the only click target that opens the main window (Electron swallows clicks inside a drag region). Its shadow must fit inside the window margin or the window edge clips it into a visible square. `bounds.js` `clampToArea` keeps it on screen (`will-move`, `moved`, display changes). `tests/mini-window.test.js` guards these.
- **Welcome tour.** `TOUR` in `app.js` is 10 steps in 4 phases; each step names a `view` and a list of CSS selectors for the ring (first one on screen wins, none means a centred card, e.g. Start is missing while a session runs). The ring is `.tour-ring` (accent token only, huge box-shadow dims the rest) and is re-placed twice a second because snapshots rebuild the page. A step that rings something new needs that element to stay findable (`#home-start`, `.pair-code`, `.mochi-box`, `#chip-streak`, `.navbtn[data-view]`); `tests/tour.test.js` checks they exist. Step text is `tour.N.t/.d` in all four languages. The About page's release link goes through `app:openReleases`, a fixed URL: StudyNook must never fetch the network by itself.
- **Ambience sounds.** `assets/sounds/{rain,waves,fire,cafe}.mp3` ship in the installer (`extraResources` → `resources/sounds`). `sound:get` in `ipc.js` looks in the user's `SOUNDS_DIR` (`%APPDATA%\StudyNook\sounds`, or `assets/sounds` in dev) first, then in `BUNDLED_SOUNDS_DIR`; with no file it falls back to the synthesized beds in `audio.js`. Keep the four files small (`tests/sounds.test.js` caps the total) and keep their credits in `THIRD-PARTY-NOTICES.md`. Do not add recordings whose license you have not checked.
- **Notes.** Each note is `{id, title, body, dir: auto|ltr|rtl, attachments: [{id, name, size, addedAt}], updatedAt}`; the body limit is 50,000 characters and appears in three places that must agree (`MAX_BODY` in `views-manage.js`, `saveNote` in `ipc.js`, `sanitizeData`). Typing is saved 450 ms after the last key, and the pending text is flushed synchronously from a `beforeunload` handler (`notes:saveNow`), because the close would otherwise lose it. The list and editor are rebuilt on every snapshot; the in-memory note object is kept current while typing so a redraw does not lose text. A global `dragover`/`drop` guard in `app.js` stops a dropped file from navigating the window.
- **PDF attachments.** `note-files.js` copies PDFs to `<data>/attachments/<noteId>/<attId>.pdf` after checking the extension, the `%PDF-` header and the size (≤ 50 MB, ≤ 20 per note). The renderer never supplies a path: it names a note and an attachment id, and the path is rebuilt from ids that match `/^[A-Za-z0-9_-]{1,40}$/`. Deleting a note, resetting data or importing data prunes files no note refers to (`pruneAttachments`). They are not part of Export data or the automatic backups (the Help page says so).
- **Localhost bridge security.** `sync-server.js` validates the Host header on every request (DNS-rebinding guard), requires the token for everything but `/ping` and `/pair`, and throttles pairing. Do not loosen these checks.
- **Clean quit waits for the extension.** The extension keeps blocking from its last synced state if the app disappears (its "ghost focus"), so a session that ends and quits within the poll interval would leave sites blocked until the old end time. The `before-quit` handler in `main.js` holds the quit (up to 8 s, `server.waitForPoll`) only when `server.staleBlockingForExt()` is true: the extension was last told "blocking on" and it is off now. Check `lifecycle.log` for `quit-held-for-extension` and `quit-released`. Do not remove the hold without re-testing an End-then-quit against the extension.

## Conventions and gotchas

- Data files are plain JSON in `studynook/data/` in dev, or `%APPDATA%`'s userData folder when packaged (`%APPDATA%\StudyNook\`: `data.json`, `session.json`, `lifecycle.log`, `watchdog-history.json`, `attachments\`, `backups\`). Don't change the `data.json` shape without updating `defaultData()` and `sanitizeData()` in `store.js`. Never edit or delete a real user's data folder while debugging; read logs only.
- Design rules (tokens, spacing scale, typography, icon mapping, settings table) live in `docs/UI-REDESIGN-SPEC.md`; watchdog/extension-finder notes in `docs/FORCE-EXTENSION-NOTES.md`; the earlier security pass in `docs/HARDENING-REPORT.md`.
- The app (`studynook/package.json`) and the extension (`extension/manifest.json`) have separate version numbers. When the extension changes (including its blocked page and strings), bump `extension/manifest.json` and `extension/version.json` together: the extension popup compares them to detect a stale worker and offers a reload. After installing a build with a new extension version the user must reload the extension once from `chrome://extensions`.
- Use the `NOOK_SMOKE` hook and `tests/smoke.js` only for end-to-end checks; unit tests should stay Electron-free.
- **Verifying behavior.** Unit tests are not enough for process and window behavior; the worst bugs here were found by really killing the app and really typing. Launch `electron.exe studynook --user-data-dir=<tmp> --remote-debugging-port=<p>` and drive it over the DevTools protocol, reproduce on the old code first (`git archive origin/main`), then verify the fix, using `data/lifecycle.log` as evidence (relaunched copies lose the debug port). A dev session starts a watchdog that relaunches the dev app: delete `studynook/data/session.json` and stop your own dev processes when done, and never kill a StudyNook you did not start. Keep scratch folders (test profiles) outside the repo so `git add -A` does not commit them.
- **Releasing.** Bump `version` in `studynook/package.json` and in `package-lock.json` (lines 3 and 9), add a section at the top of `CHANGELOG.md`, run lint, tests and a real Electron boot (`NOOK_SMOKE=1`), then `npm run dist` and check the exe's icon and version. `THIRD-PARTY-NOTICES.md` and `LICENSE` are copied into the installer through `extraResources`: update the notices when you add a bundled dependency, font or icon set. The installer is unsigned (Windows shows an "unknown publisher" warning); a silent install (`/S`) fails with exit code 2 while StudyNook is running. Publishing the GitHub release (tag `vX.Y.Z`, attach `StudyNook-Setup-X.Y.Z.exe`) is done by the repo owner. `.github/workflows/build-installer.yml` builds the same installer on a GitHub-hosted Windows runner (run it by hand, or push a `v*` tag; it checks the tag equals `package.json`'s version, runs lint and tests, builds, checks the exe's product name and version, and uploads the installer plus a `.sha256` as a workflow artifact). It does not publish a release and does not sign. It is the base for SignPath Foundation signing, which needs builds made on a trusted CI system; add the signing step only after approval, and add the required "Code signing policy" section to the README and site at the same time, not before.
- **PRs and issues.** Give pull requests a title that says what changed (not "Update"); the template asks how it was checked. Bugs and plans go in Issues, not in PR titles.
